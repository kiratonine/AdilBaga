## 3. `sync:compare` (полный bundle A против узкого B)

```
[sync:compare] A=3281 B=3279 onlyA=2 onlyB=0 priceChanged=0 mismatch=0.06% (max 1.00%)

```

Код 0, расхождение 0,06% при пороге 1%. Различий в ценах нет. Два товара есть только в A:

- `DINA:11594` «Рулет куриный с сыром вес»: категория `2` («Готовая еда») входит в набор, в ней было 93 товара при полном скрапе и 92 через ~12 минут при узком. Скорее всего, товар пропал из наличия между прогонами или сдвинулась выдача между проходами. Это не дыра в наборе категорий.
- `FIX_PRICE:fp_1606147` «Лапша с тушёной говядиной, Мастер Кан, 100 г»: в полном скрапе есть только в промо-подборке «Азиатские хиты», которая не входит в `produkty-i-napitki`. Словарь относит товар к публикуемой категории, поэтому он есть в A и нет в B. Это принятый постоянный пробел узкого скрапа (1 из 74 товаров Fix Price в scope при этой проверке): товары, которые есть только в промо-подборках вне `produkty-i-napitki`, ежедневный прогон не видит. Еженедельный полный скрап их тоже не публикует: `weekly-full-scrape.sh` ничего не загружает в БД, а ежедневный прогон `data/sources-full` не читает. ### 5.1 Разовый `-recluster` (нужен из-за старого дампа)

Первый запуск `daily-sync.sh` прошёл скрап и `pnpm sync`, но строгий dry-run остановился:
`error_code=ingestion_validation_failed` (`raw_count=3279`, `reused_count=118`, `new_count=579`), `[sync] publish step failed`, код **1**.

Код гейта `cmd/ingest` на dry-run в журнал не пишет. Его восстановили, пересчитав `resolve` по bundle и связкам товар → карточка прошлого snapshot. Первая ошибка — **`canonical_split_conflict`** на группе 698 из 3 038. Всего против baseline 8 split и 4 merge: например, «Сахар-рафинад Max Swееt 350 г» `DINA:7944` + `DANA:dana_15860` раньше были двумя карточками. С полным bundle A картина та же, значит дело не в узком скрапе.

Причина: дамп 2026-10-05 содержит только `baseline-internal-v1` (863 товара) с группировкой до словаря SCRUM-7. Прод этот переход уже сделал разовым `-recluster -apply` (SCRUM-7 docs). По `SYNC_RUNBOOK.md` §4 такие конфликты снимаются через `-recluster`, поэтому в одноразовой локальной БД сделан тот же шаг: свежая БД из дампа, затем на bundle текущего прогона:

| `cmd/ingest -recluster -apply` | `applied:true`, те же метрики, `frontend_revalidation outcome_class=degraded`, snapshot `5f48b7d9…` `published` |

Дальше всё шло без `-recluster`, в строгом режиме.

## 7. Отклонения от плана

1. **Dina: 14 категорий вместо ~50** (spec §4.2). Покрытие 2019/2019, страниц и запросов (166 и 9) даже меньше оценки, `sync:compare` пройден. Формулировку в spec стоит поменять на «14 категорий, 166 страниц, 9 запросов».
2. **Общее время ~224–228 с вместо 1–1,5 мин.** Dina (22–24 с), Fix Price (21–22 с) и ingest (< 1 с) укладываются в цели. Критический путь — Dana: HTML-скрапер без изменений, 178 страниц с паузой 300 мс, 222–226 с. Spec §5 закладывал ~1 мин. Ускорение Dana — отдельная задача (spec §6).
3. **Расхождения A/B — только `fp_1606147`** (товар только в промо-подборке Fix Price вне `produkty-i-napitki`) и **`DINA:11594`** (вероятно, выбыл из наличия между прогонами). Пробел по промо-подборкам Fix Price постоянный и принят (1 из 74 товаров в scope): еженедельный полный скрап его не закрывает, потому что ничего не публикует. Исправление на потом — алиасы промо-подборок в `FIXPRICE_SCOPE_ALIASES`.
4. **«Было» — полный скрап `SCRAPE_ALL=1`** (~25 мин), а не прежний ежедневный прод-режим: у Dina и Dana там уже был ограниченный обход по корням, и прод-прогон, по замеру владельца, занимал ~20 мин. Поэтому выигрыш против прежнего ежедневного прогона — ~20 мин → ~4 мин, меньше, чем в таблице §1. Замеры в §1 при этом верны для своей базы.
5. **Нужен был разовый локальный `-recluster -apply`** (§5.1). Дамп 2026-10-05 старше словаря SCRUM-7, и первый строгий dry-run падал на `canonical_split_conflict` (8 split, 4 merge). План (шаг 7) в этом случае предлагал попросить у владельца свежий дамп prod; контроллер вместо этого выбрал описанное в runbook средство — `-recluster` в одноразовой локальной БД. Поэтому строгий прогон шага 8 шёл по БД, уже пересобранной `-recluster`, и **совместимость с прод-БД не доказывает**. Ожидаем, что прод (он уже прошёл переход SCRUM-7) примет bundle без этого шага, и локальная проверка со свежим дампом prod, вероятно, тоже прошла бы, но это не проверено. Task 10 обязан начать со строгого dry-run на проде без `-recluster`: `newCanonicalCount` близок к 0, merge и split — 0. Если merge или split не нули — остановиться, `-apply` не запускать; `-recluster` на проде — только по решению владельца.
6. Шаг 8 выполнялся дважды: первый запуск (код 1) остановлен гейтом из п. 5, второй — после `-recluster` (код 0). Каждый запуск скрипта заново скрапит три сети.
7. Dana 2026-10-13 работала (HTTP 500 не было), подмена `dana.json` и `SYNC_MAX_SOURCE_AGE_HOURS` не понадобились.
8. У Fix Price в `sourceStats` нет счётчика запросов, поэтому число запросов в §2 расчётное.
