# Быстрое автоматическое обновление цен на проде — дизайн

Дата: 2026-10-13. Статус: черновик на ревью.

## 1. Цель

Цены на проде обновляются автоматически дважды в день (06:00 и 18:00 по Актау), и один прогон занимает **~1–2 минуты вместо ~20**. Падение одной сети не блокирует обновление двух других.

### Решения владельца (2026-10-13)

- Запуск — VPS, systemd-таймер (`ops/sync/`). Ingest-креды остаются только на VPS.
- Частота — 2 раза в день; ускоряем сам прогон.
- Скрапим только публикуемый scope (9 категорий `DEFAULT_PUBLISH_CATEGORIES`). Полный каталог — `SCRAPE_ALL=1`, отдельным еженедельным прогоном.
- Источники — JSON-API магазинов, ответы проходят через адаптер, знающий формат. Dana — опционально (см. §6).

### Проверенные возможности API

- **Dina** (`backend.dinamarket.kz/api/v1.1/customer/graph`): `_limit` режется до 24, аргументов `ids`/`search` нет, интроспекция закрыта. **Алиасы GraphQL работают**: 40 алиасов `pN: products(...)` в одном запросе вернули 960 уникальных товаров за ~9 с.
- **Fix Price** (`api.fix-price.kz/buyer/v1/product/in/{alias}`): максимум 28 товаров на страницу при любом `limit`; заголовок `x-count` = общее число. `produkty-i-napitki` = 812 товаров.
- **Dana**: публичного JSON нет (`/rest/` — Bitrix REST с авторизацией). Есть мобильное приложение `kz.dana.aktau` — вероятно, с JSON-бэкендом на `dana-market.kz`. На 2026-10-13 сайт отдаёт 500 на все PHP-страницы (переполнена их таблица `b_stat_session`).

## 3. Архитектура

Модель не меняется: `scrapers/*` → `data/sources/*.json` (zod `SourceFile`) → `pnpm sync` (словарь) → `data/sync/bundle.json` → `cmd/ingest` (dry-run, затем `-apply`, атомарный snapshot, revalidation фронта). Go ingest, схема БД, quality gates и фронт не меняются.

Меняются только: что и как скрапим, как запускаем скраперы, как `sync` выбирает файлы источников, и установка на VPS.

```text
                ┌─ scrape:dina  (GraphQL, батч 20 страниц/запрос, категории scope) ─┐
daily-sync.sh ──┼─ scrape:fixprice (REST, алиасы scope)                             ├─ wait ─→ pnpm sync ─→ ingest dry-run ─→ ingest -apply
  (параллельно) └─ scrape:dana  (HTML, как сейчас)                                  ┘   (берёт последний удачный файл упавшей сети, если он < 36 ч)
```

## 4. Компоненты

### 4.1 Dina: батчинг GraphQL

- Новая функция собирает один GraphQL-документ из N алиасов `p<i>: products(shop_id, _page, _limit: 24, category_id)` и разбирает ответ обратно в страницы. Маппинг товара — существующий `mapDinaItem`, без изменений.
- `DINA_BATCH_PAGES = 20` (не 40: полнее ответ за меньшее время на их стороне и меньше риск бана). Пауза `politeFetch` между батчами сохраняется.
- Обход в два прохода, батч смешивает категории:
  1. Страница 1 всех категорий набора, по 20 алиасов в запросе. `pageInfo.total` каждой категории даёт число её страниц.
  2. Все оставшиеся пары (категория, страница) одним списком, нарезанным по 20 алиасов.
  Так маленькие категории не тратят пустые алиасы, а число запросов ≈ ⌈всего страниц / 20⌉.
- Ошибка в одном алиасе (`errors` в ответе при наличии `data`) считается ошибкой страницы и идёт в `errorCount` (порог 10, как сейчас).
- Fallback: `DINA_BATCH_PAGES=1` даёт прежнее поведение (одна страница — один запрос).

### 4.2 Dina: категории scope

- Сейчас: 15 корней + подкатегории, найденные у товаров → товары скачиваются по нескольку раз.
- Новое: файл `data/mapping/dina-scope-categories.json` — минимальный набор `category_id`, покрывающий все товары Dina, которые по словарю попадают в публикуемые категории (жадное покрытие множества по `rawPayload.categories` полного source-файла). Оценка на данных 06.10: ~50 категорий, ~190 страниц → ~10 батч-запросов.
- Генерирует файл команда `pnpm scope:dina` (вход: `data/sources/dina.json` из полного прогона + `dictionary.json`; выход отсортирован, коммитится в git).
- Если файла нет или он пуст — fallback на текущий обход по `DINA_SCOPE_ROOTS`. `SCRAPE_ALL=1` — полный каталог, как сейчас.
- Новый товар в категории вне набора не попадёт в ежедневный прогон — он подхватывается еженедельным полным прогоном (§4.6), после которого набор пересчитывается.

### 4.3 Fix Price: алиасы scope

- `FIXPRICE_SCOPE_ALIASES = ['produkty-i-napitki']`. Ежедневный прогон обходит только их (~30 запросов вместо ~300); `SCRAPE_ALL=1` — все алиасы из `category/menu`.
- Размер страницы — 28 (фактический максимум API). Конец категории — по `x-count` или короткой странице.
- Проверка: если алиаса из списка нет в `category/menu` — ошибка скрапера (магазин переименовал категорию; молча публиковать 0 товаров нельзя).

### 4.4 Параллельный запуск и отказоустойчивость

- `daily-sync.sh` запускает три `pnpm scrape:*` фоном, ждёт каждый и пишет в журнал код выхода и длительность каждой сети.
- Упавший скрапер не перезаписывает `data/sources/<store>.json` (это уже гарантирует атомарная запись `writeSourceFile`), поэтому там остаётся последний удачный файл.
- `pnpm sync` работает как сейчас: `assertFresh` отказывает, если файл сети старше `SYNC_MAX_SOURCE_AGE_HOURS` (36 ч). Значит, старые цены упавшей сети публикуются не дольше 36 ч, и `capturedAt` у неё честный — фронт уже показывает предупреждение для цен старше 36 ч.
- Ingest-гейты (`store_count_drop`, `required_source_missing`) не меняются.
- Если упали все три скрапера — `sync` и ingest не запускаются (новых цен нет; повторно публиковать старые файлы бессмысленно).
- Если упала хотя бы одна сеть, скрипт после публикации завершается с ненулевым кодом → `systemctl status aktau-sync` = `failed`, проблема видна в журнале.

### 4.5 Защита от смены формата

- zod-схема `SourceFile` и фикстуры в `pipeline/test/fixtures` остаются контрактом адаптера.
- Новые фикстуры: батч-ответ Dina (2–3 алиаса, один с ошибкой) и ответ Fix Price на 28 товаров с `x-count`.

### 4.6 Расписание на VPS

- `aktau-sync.timer` (уже есть): 01:00 и 13:00 UTC, ежедневный быстрый прогон с `-apply`.
- Новый `aktau-sync-full.service` + `.timer`: раз в неделю (вс 22:00 UTC) — `SCRAPE_ALL=1` скрапы и `pnpm scope:dina`, **без** ingest. Обновляет полные source-файлы и `unmapped.json` для еженедельной обработки новых товаров.
  - Чтобы полный прогон не затёр узкие ежедневные файлы, он пишет в `data/sources-full/` (параметр `SOURCES_DIR`), а `scope:dina` читает оттуда.
- Новый `dina-scope-categories.json` из полного прогона не применяется автоматически: изменение видно в `git diff`, человек коммитит. Так набор категорий меняется осознанно.
- `TimeoutStartSec` ежедневного юнита снижается с 2 ч до 20 мин.
- Установку выполняет владелец по `ops/sync/README.md` (у агента нет SSH-доступа к VPS).

## 6. Dana (опционально, вне основного объёма)

Отдельная задача, начинается только после того, как получен JSON-запрос мобильного приложения `kz.dana.aktau` (снятие трафика HTTP Toolkit/mitmproxy или APK с телефона владельца). Тогда пишется `mapDanaItem` (JSON → `SourceProduct`) с фикстурой, по образцу Dina/Fix Price. `sourceProductId` должен остаться совместимым со словарём (`dana_<id>`), иначе нужен перенос ключей словаря. До этого Dana — HTML-скрапер, защищённый fallback'ом §4.4.

## 7. Проверка эквивалентности перед включением

Один ручной прогон на машине разработчика:

1. Полный прогон (`SCRAPE_ALL=1`, старый код) → bundle A.
2. Новый узкий батч-прогон → bundle B.
3. Скрипт `pnpm sync:compare A B`: множества in-scope идентичностей `store:sourceProductId` и цены совпадают; допускается расхождение ≤1% (товар исчез между прогонами). Отчёт идёт в описание PR.

## 8. Тестирование

- vitest: сборка и разбор батч-документа Dina (включая частичные `errors`); обход категории батчами с остановкой по `total`; генерация `dina-scope-categories.json` (детерминированное покрытие); фильтр алиасов Fix Price и ошибка на отсутствующий алиас; размер страницы 28 и `x-count`; `SOURCES_DIR`.
- `sync.test.ts`: свежий файл одной сети и файл второй сети возрастом 20 ч → bundle собирается; файл возрастом 40 ч → отказ (поведение уже есть, закрепляем тестом для сценария «скрапер упал»).
- `daily-sync.sh`: `shellcheck`; локальный прогон с одним заведомо падающим скрапером (неверный `FIXPRICE_CITY_ID`) → остальные публикуются в dev-БД, код выхода ≠ 0.
- Go ingest не меняется → существующие тесты.
